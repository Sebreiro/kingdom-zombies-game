<decisions>
## Implementation Decisions

### Root cause (established before planning)
- Godot 4.7.2 on Windows has a race on the process-wide working directory. `DirAccessWindows::DirAccessWindows()` reads the cwd without a lock in two calls. It calls `GetCurrentDirectoryW(0)` for the size, resizes the buffer without initializing it, then calls `GetCurrentDirectoryW(n)` and ignores the result. `DirAccessWindows::change_dir()` sets the process cwd to another directory for a moment under `GLOBAL_LOCK_FUNCTION`, which the constructor does not take.
- If another thread makes the cwd longer between the two reads, the fill call writes nothing. The uninitialized heap buffer is then decoded as UTF-16 in `String::utf16()` (the first diagnostic block). The constructor's `change_dir(".")` converts it back with `.utf16()` twice, which adds the next two blocks.
- In all four failing runs, the stale heap bytes matched the tail of a `.fontdata` file the same import had just compressed. Fonts import on worker threads because `ResourceImporterDynamicFont::can_import_threaded()` returns true. That explains why the diagnostics vary between runs and appear only in some imports.
- The project setting `editor/import/use_multiple_threads` (default `true`) enables threaded import. With it set to `false`, imports run on one thread and the race cannot happen.

### Where to fix
- The engine binary is pinned and official, so it cannot be patched here. The fix goes in the harness that starts every editor import: the `command()` choke point in `tools/phase4/check.cjs`.
- For every command with `--import`, the runner checks that `--path` names a run-owned project under `context.directory` that contains `project.godot`. It then makes sure that file sets `[editor] import/use_multiple_threads=false` before it starts the process.
- `override.cfg` cannot be used because the editor ignores it (`ProjectSettings::setup(..., p_ignore_override)` in editor mode).

### Policy strictness
- A project that already sets `import/use_multiple_threads=false` is left byte-identical. (Amended after code review: only a file that already ends with the canonical single-thread block is left unchanged. Every other file gets the block appended last, because Godot keeps the last value it reads, so a misread `false` can no longer skip the append. See `261120-09v-REVIEW.md`, Disposition.)
- A project that sets it to anything else (for example `true`) is rejected before spawn with `EDITOR_IMPORT_THREADED`. The runner does not rewrite a value a case chose explicitly.
- An `--import` command whose `--path` is missing, outside the run-owned directory, or has no `project.godot` is rejected with `EDITOR_IMPORT_PROJECT` before spawn.
- Commands without `--import` (`--script`, `--export-*`, `--build-solutions`, `--version`) are not changed.

### Claude's Discretion
- The test is a `node:test` self-test mode inside `tools/phase4/check.cjs`, run with `node tools/phase4/check.cjs --self-test-editor-import`. It uses a Node child process as a stand-in for Godot so it never needs the engine binary, and it runs before the fix to prove it fails. (Revised after research: a new tracked test file would break the Phase 1 `REPOSITORY_EXACT_TRACKED_UNION` proof and require catalog and hash updates. `tools/phase4/check.cjs` is an `outside-validator` source with no pinned content hash, so editing it is safe. Phase 4 already uses self-test modes, for example `export-profile.cjs --self-test-helper`.)
- No new tracked files outside `.planning/`.
- `.planning/debug/phase04-import-surrogates.md` is updated to `resolved` with the root cause, the evidence and the fix.
- The game project `src/godot-game/project.godot` is out of scope. Developer editor sessions there are not harness proofs, and changing game settings needs separate approval. It is noted as a follow-up.
- Reporting the engine defect to Godot upstream is out of scope and noted as a follow-up.

</decisions>

<specifics>
## Specific Ideas

- Every harness `--import` invocation already passes `--path <project>` under the run's own directory. Most cases write their own `project.godot` inline. The policy therefore lives in `command()`, not in roughly 20 call sites.
- Evidence from a non-intrusive Frida trace (observation only, no timing changes) on the original failing animation fixture, four runs each:
  - Threaded import: 13 threads touched the cwd, and 4, 4, 3 and 0 `GetCurrentDirectoryW` fills failed.
  - `use_multiple_threads=false`: 1 thread touched the cwd and 0 fills failed in all four runs, with the same 6912 events and 1142 size/fill pairs.
- The 44 imported files are byte-identical between threaded, single-threaded and the original failing run.

</specifics>
