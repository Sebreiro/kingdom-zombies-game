# Quick Task 261119-15c: Code Review Report

**Reviewed:** 2026-11-20T00:10:00Z
**Depth:** quick (careful pass; every data-loss claim below was reproduced against throwaway fixtures)
**Files Reviewed:** 8

## Summary

I reviewed the cleanup CLI, its tests and the cleanup docs, plus the small doc diffs against `origin/dev`. The existing suite passes (7/7, Node 24 at the Codex runtime path). I then ran a probe script against temporary git repositories in my own temp folder, which I deleted afterwards. Git was 2.56.1.windows.1 and Node was 24.

Verified safe:
- `fs.rmSync` in Node 24 unlinks a Windows junction without following it. This holds for a junction as a direct child of `.phaseN` and for one nested deeper. The sentinel target survived in both cases.
- A `.phaseN` root that is itself a junction is skipped, because `lstat` does not report it as a directory.
- Paths with spaces in the worktree porcelain output parse correctly. Git emits LF there, and the parser also accepts CRLF.

Reproduced problems:
- The tool deletes a linked worktree nested inside `.phaseN`, even after its own worktree check reported the worktree as dirty.
- Its "clean" check depends on the user's git config.
- `git worktree remove` exits 0 but leaves the worktree folder behind when the folder contains junctions. Task worktrees are set up exactly this way, with `.phase1/{cache,...}` junctions into the main checkout. The tool then reports `removed` and leaves an orphan folder that still points into the pinned toolchain and Linux VM disk.

## Critical Issues

### CR-01: A linked worktree nested in an ignored `.phaseN`/`.planning/tmp` root is deleted with its uncommitted work, bypassing every worktree safety check

**File:** `tools/workspace-cleanup.cjs:66-76` (classification), `:134-141` (deletion), `:167-180` (artifacts are deleted before worktree state is consulted)
**Issue:** `classifyRoot` marks every direct child of an ignored root `delete`. It never checks whether a child is, or contains, a registered linked worktree or any other git repository (`.git` file/dir). `git ls-files` and `git check-ignore` do not see into a nested worktree, so the "tracked files" guard cannot catch it. Reproduced:

1. `git worktree add -b feature/nested .phase4/wt`, then write `.phase4/wt/precious.txt`.
2. A dry run prints `delete .phase4/wt (phase output)`. In the same output it lists the worktree `.../.phase4/wt [feature/nested] (uncommitted changes)` as `keep`.
3. `--apply` runs `rmSync(.phase4/wt)`. `precious.txt` is gone and the worktree record is left dangling.

The docs say worktrees go to the system temp folder, but nothing enforces that. Older agents or GSD flows that put worktrees or scratch clones under `.phaseN` lose uncommitted work.
**Fix:** Before deleting anything, compute the set of worktree paths from `planWorktrees` and refuse any artifact whose path equals or contains one. Also refuse any child that contains a `.git` entry. For example:
```js
const worktreePaths = worktrees.filter(w => !w.main).map(w => path.resolve(w.path));
const containsWorktree = rel => worktreePaths.some(w => {
  const r = path.relative(path.resolve(root, rel), w);
  return r === '' || (!r.startsWith('..') && !path.isAbsolute(r));
});
// in classifyRoot/run: if (containsWorktree(child) || fs.existsSync(path.join(root, child, '.git'))) -> keep 'contains a Git worktree or repository'
```
Compute worktrees before artifacts in `run()`, and add a regression test.

### CR-02: The "uncommitted changes" check depends on user config, so `status.showUntrackedFiles=no` lets untracked work be destroyed

**File:** `tools/workspace-cleanup.cjs:121`
**Issue:** `git status --porcelain` respects `status.showUntrackedFiles`, `diff.ignoreSubmodules` and `submodule.*.ignore`. Reproduced: with `git config status.showUntrackedFiles no`, a pushed worktree containing an untracked `new-work.txt` was reported `removable (clean and pushed)`. `--apply --remove-worktree` then deleted it with exit code 0. Git's own `worktree remove` check is fooled by the same config, so the tool's check is the only protection and it fails. `showUntrackedFiles=no` is a common speed setting on large Windows checkouts.
**Fix:**
```js
git(worktree.path, ['status', '--porcelain=v1', '--untracked-files=all', '--ignore-submodules=none'])
```
Add a test that sets `status.showUntrackedFiles=no`.

### CR-03: `git worktree remove` leaves junctions behind but the tool reports `removed`, leaving an orphan folder linked into the pinned toolchain and VM disk

**File:** `tools/workspace-cleanup.cjs:195-198`; docs `docs/workflow/cleanup.md:40`
**Issue:** Task worktrees are set up with `.phase1/{cache,cli-home,dotnet-home,feed,http-cache,packages,tools}` as junctions into `D:/Work/Games/KingdomZombies/.phase1/...`; the review worktree itself is set up this way. Reproduced with Git 2.56.1.windows.1:

1. Create a worktree whose `.phase1/cache` is a junction to the main checkout's `.phase1/cache`.
2. `git worktree remove <wt>` exits 0 and drops the worktree record.
3. `<wt>/.phase1/cache` (the junction) and its parent folders are still on disk.

The tool logs `removed <wt>` and exits 0. The docs promise that removal deletes the ignored outputs. The orphan folder is now outside every checkout, so this tool will never clean it again. The docs then send the creator to delete it by hand. In Windows PowerShell 5.1, the project's primary shell, `Remove-Item -Recurse -Force` on such a folder can recurse through the junction into the main checkout's pinned toolchain and Linux VM disk.
**Fix:** Before `git worktree remove`, unlink every junction or symlink in the worktree's ignored roots: `lstat().isSymbolicLink()` then `fs.unlinkSync` or `fs.rmdirSync`, never a recursive delete. After `git worktree remove`, confirm with `fs.existsSync` that the path is gone. If anything remains, delete it with `fs.rmSync` (Node 24 does not follow junctions; verified). If the path still exists after that, report `failed`. Add a junction regression test that runs on win32.

## Warnings

### WR-01: The pinned `.phase1` cache names are matched case-sensitively on Windows

**File:** `tools/workspace-cleanup.cjs:8,72`
**Issue:** `DURABLE_PHASE1.has(name)` is case-sensitive, but NTFS and git (`core.ignorecase=true`) are not. Reproduced: `.phase1/Tools/linux-vm/disk.img` is classified `delete .phase1/Tools (phase output)`. Any tool, script or user that creates or renames one of these folders with different casing loses the VM disk or toolchain on the next `--apply`. These folders "must never be deleted".
**Fix:** On win32, compare `name.toLowerCase()` (and on Linux too, for safety). Better still, invert the default for `.phase1`: keep anything whose lowercased name is in the set, and log it.

### WR-02: The tool deletes the live `.phase1/check.lock` and runs of an in-progress checker

**File:** `tools/workspace-cleanup.cjs:70-75`; docs `docs/workflow/cleanup.md:9`
**Issue:** `tools/phase1/check.cjs:169-172` uses `.phase1/check.lock` as an exclusive lock and states that "interrupted locks require inspection". The cleanup tool classifies `check.lock` and `.phase1/runs` as `delete` regardless. During this review the lock existed in the review worktree while a check was running. `--apply` at that moment deletes the active run's output and the lock, so a second checker can start concurrently. It also silently clears stale locks that policy says need inspection. The docs forbid cleaning while a run is active, but the tool does not enforce it.
**Fix:** If `.phase1/check.lock` exists, refuse `--apply` with exit code 1, or keep `.phase1` entirely with reason `checker lock present`. Do the same for any other known lock files.

### WR-03: The docs promise that every `.phaseN` output is deleted, but the tool only deletes roots listed in `.gitignore`, and the docs never say to add them

**File:** `docs/workflow/cleanup.md:29,35`; `.gitignore` on this branch (based on `dev`) ignores only `/.phase1/`-`/.phase3/`
**Issue:** On `dev`, `.phase4/` (the 74 GB example) and every later `.phaseN/` are not ignored. The tool prints `keep .phase4 (not ignored by Git)` and deletes nothing. That outcome is safe but contradicts the table ("every later `.phaseN/` folder ... Delete"). Line 35 says a new output location "needs a `.phaseN` subfolder" but omits the `.gitignore` entry the tool requires. Agents following the docs will believe cleanup happened.
**Fix:** In cleanup.md, state that each `.phaseN/` root must be listed as `/.phaseN/` in `.gitignore` before use. Alternatively, add a generic `/.phase[0-9]*/` ignore rule in the same change, and note that a non-ignored root is kept and reported.

## Info

### IN-01: Assume-unchanged and skip-worktree edits, and the detached-HEAD reflog, are lost when a worktree is removed

**File:** `tools/workspace-cleanup.cjs:121-124`
**Issue:** Reproduced: after `update-index --assume-unchanged README.md` and a local edit, the worktree was reported clean and was removed, edit included. A detached worktree whose HEAD was moved back onto a pushed commit loses its per-worktree reflog, and with it any commits that only the reflog still reached. A worktree stopped mid-rebase, merge or bisect on a pushed commit is also reported removable.
**Fix:** Refuse when `git ls-files -v` shows lowercase or `S` flags. Also refuse when `rebase-merge`, `rebase-apply`, `MERGE_HEAD` or `BISECT_LOG` exist under `git rev-parse --git-dir` of that worktree.

### IN-02: Any git failure aborts the whole run with a stack trace

**File:** `tools/workspace-cleanup.cjs:121-122,130,157`
**Issue:** These calls throw on any git failure: running outside a repository, a worktree folder whose `.git` file is broken, or an unborn or corrupt HEAD. An uncaught exception results (exit 1, raw stack), and that one broken worktree also blocks artifact cleanup. Nothing is deleted, but the documented exit codes (1 = deletion or removal failure, 2 = arguments) no longer describe the outcome.
**Fix:** Catch the error per worktree and record `{removable: false, reason: 'git failed: ...'}`. In `run()`, wrap `rev-parse` and return 2 with a clear message.

### IN-03: A refused `--remove-worktree` does not stop artifact deletion

**File:** `tools/workspace-cleanup.cjs:167-204`
**Issue:** If the user mistypes a worktree path, the tool still deletes every artifact and then exits 1. Users who pass a worktree usually expect an all-or-nothing preflight.
**Fix:** Resolve and validate `requested` before the deletion loop, and abort `--apply` if any requested worktree is refused.

### IN-04: The `prune` label and the "pruned" message are wrong for locked, missing worktrees

**File:** `tools/workspace-cleanup.cjs:119-120,187-190`
**Issue:** The missing-folder check runs before the `locked` check. A locked worktree on an unplugged drive is therefore labelled `prune`, but `git worktree prune` skips locked entries. The tool still prints `pruned missing worktree records`, and the worktree stays listed.
**Fix:** Check `locked` before the missing-folder test, or report `missing (locked; not pruned)`.

### IN-05: Worktree porcelain is parsed without `-z`

**File:** `tools/workspace-cleanup.cjs:100-113,130`
**Issue:** Git C-quotes paths that contain newlines or other unusual characters when `-z` is not given. A quoted path then never matches `samePath`, so the worktree is refused (a false negative, not data loss).
**Fix:** Use `worktree list --porcelain -z` and split on `\0`, with an empty field ending each record.

### IN-06: The tests cover none of the Windows or data-loss edge cases above

**File:** `tools/workspace-cleanup.test.cjs`
**Issue:** No test covers junctions inside `.phaseN` or inside a worktree being removed, a nested worktree in `.phaseN`, case variants of the durable names, config-sensitive status, or running the tool from inside a linked worktree.
**Fix:** Add regression tests for CR-01 to CR-03 and WR-01 to WR-02, with the junction tests guarded by `process.platform === 'win32'`.
