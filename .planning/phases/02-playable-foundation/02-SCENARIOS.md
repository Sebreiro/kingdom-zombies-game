# Phase 2 Scenarios

All 16 active Phase 2 cases below are selected: they are new or changed in this phase. None is omitted. Future-phase cases remain planned. Executable identities and required image checkpoints are in [the catalog](../../../tools/phase2/required-cases.json); commands, bounded waits, cleanup and evidence formats are in [foundation checks](../../../docs/workflow/foundation-checks.md). BASE-01–03 and [AC-01–13](02-SPEC.md#acceptance-criteria) supply the expected behavior, subject to the creator's current testing amendment.

## Run groups

- `phase2-core`: no game window; `core.authority`, `core.input`, `core.lifecycle`, `core.permissions`. Preconditions: pinned toolchain, current compiled tests. Each case has independent pure/compiled proof state and a distinct report result.
- `phase2-runner`: no game window; `runner.integrity`, `runner.processes`, `runner.repeatability`. Owned synthetic child processes and invocation directories are isolated and cleaned up.
- `phase2-foundation-window`: one Windows game process at 1280×720; ordered `rendered.menu`, `rendered.tracer`, `rendered.directions`, `rendered.distance`, `rendered.world`, `rendered.lifecycle`, `rendered.focus`, `rendered.resources`, `rendered.quit`. Preconditions: complete implementation, clean code review/fixes, passing prerequisites, pinned engine and owned foreground window. Use ordinary Escape/Start to reset between compatible scenarios. One-shot recoverable entry failure is consumed by the first menu scenario. Quit runs last. No additional process is selected.

Every rendered scenario uses actual keyboard/mouse input, fresh session/actor state after reset, nonce-bound state observations, the catalog's saved PNG checkpoints and the shared native log. Keep failures/partial evidence, release owned input and attempt the normal menu reset before continuing. If the process or reset is unusable, mark remaining dependent cases blocked. Repair selection uses the original report's failed/blocked IDs; preserve original passing records.
