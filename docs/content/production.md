## Index and output contract

Schema version 1 uses `id`, positive integer `version`, explicit `status`, `acceptanceOwner`, `shards`, `origins` and `outputs`. Shards identify their exact project-relative `path`, stable `id`, owning plan, and pending/selected status. Selected shards add content `version`, byte count and SHA256. They resolve by identity, without directory enumeration. Pending shard rows never supply resources or coverage.

Every output records its independent stable `id`, name, positive integer `version`, shard, project-relative path, byte count, SHA256, reuse/adapt/generate route, exact selected origins, production bundle, selected packaged dependencies, applicable metadata, applicability, inspection route/dependency, evidence and obligation mappings. Image metadata keeps dimensions and registration distinct from display scale. A production record contains a nonempty recipe and its SHA256. Generation records preserve their source/recipe rather than claiming unchanged reuse.

Recovered origins identify owning file, type, object ID, name, owning-file hash, retained raw object hash, exact stream paths/ranges/whole-file and range hashes, and selected object dependencies. Object IDs are local to an owner; names are never lookup keys. The retained production record must match that exact origin, recipe and raw-source identity. Original source locators are data. The runtime/clean source checks resolve packaged project files; no recovery folder is required. Authoring donor-preservation checks remain separate, read-only operations.

Distinct output IDs may share byte paths only when both declare the same nonempty `sharedFileId` and hash. Each retains its own production ID, origins and obligation mappings. Repeated import never creates duplicate identities. Existing output identities are immutable in a publication lineage: changing them requires a separately reviewed version/update contract. Pending shards can become selected at the same exact path/owner, and a selected shard can advance its explicit version while retaining its already published outputs.

Evidence separates `source` and `native` (pending/verified), `listening` (pending/accepted/not-applicable) and `judgment` (pending/accepted). A claimed pass requires a packaged exact evidence reference containing current case/invocation and matching output ID/version/hash. Old pass records, arbitrary status text, metadata-only rows or historical V/M/C cannot supply credit. Source/headless runs do not accept appearance or audio suitability. A partial obligation never becomes completed coverage. All expected IDs remain visible in diagnostics; invalid entries identify output ID/path/problem while unaffected outputs remain valid and inspectable. Actual native, listening and separate judgment acceptance belongs to plans 04-32/04-33.

## Authoring API and publication protocol

[The content module](../../tools/phase4/content.cjs) exports `expected`, `validate`, `resolveOrigin`, `merge`, `publish`, `readPublished` and `recoverPublication`, plus bounded parsing/path/file helpers. A caller supplies `publish({sourceRoot,index,publicationRoot,invocation})`. The invocation is a fresh lowercase ASCII identifier. The optional synchronous `observe(step)` supports bounded interruption controls; it supplies no validation or completion credit.

Publication destinations must be inside the project-owned `.phase4/` state or `production/phase4/published/`. Donor roots and other destinations are denied before writing. Paths use portable ASCII segments, exact ordinal spelling, no traversal, device names, percent encoding, alternate streams, aliases, links or reparse ancestors. Strict UTF-8 rejects BOMs/invalid encoding; strings preserve NFC identities and stable output IDs use lowercase ASCII. JSON rejects duplicate/unsafe keys, excessive nesting/counts and nonfinite values. Files are nonempty, regular, single-link and bounded to 32 MiB each/256 MiB selected bytes.

The writer takes `publication.lock` exclusively and records invocation/PID. It validates actual source bytes, copies exactly those selected immutable bytes into `stage-<invocation>`, validates that staged tree, then renames it to `generations/<invocation>`. Only after this validation does an atomic rename replace `current.json`. Its pointer binds invocation, generation, index hash and honest complete/incomplete status. Readers verify the pointer, index and every selected byte. A validated partial pack may publish with Incomplete status; an index claiming Complete with any missing obligation/evidence fails. Missing outputs, identity mutation or loss of already validated outputs cannot replace the current publication.

Normal failures clean only their owned stage, temporary pointer and unreferenced generation. Successful generations are retained. A hard interruption leaves a lock and possibly owned staging data. New writers fail closed. Explicit `recoverPublication({publicationRoot,invocation})` verifies the exact lock owner and that its PID no longer exists, validates the current publication, then removes only that dead invocation's unreferenced files and lock. It refuses live owners, mismatched invocation and redirected paths. PID reuse therefore refuses recovery rather than stealing another process's lock. Recovery records Interrupted, never Verified, and does not borrow the current pointer's earlier success.

## Reusable source scenarios

Run `node tools/phase4/check.cjs --case source.provenance` or `--case source.publication`. `--list` exposes the saved setup, importance/rationale, actions, expected result, evidence and ordered G0 grouping. Both are Critical source/headless cases and open no game window or audio playback. The existing `source.tracer` and `source.tracer-failures` are affected regressions for the registry loader change; they retain their original scenarios.

`source.provenance` validates the exact independent census and the actual bow bundle, then independently exercises H01 same-name owner/type lookup and explicit shared bytes; H02 absent origin/version/recipe/hash/dependency/evidence and stale evidence; H03 case, normalization, UTF-8, duplicate-key and path controls; H04 shuffled source/shard/output order; basic H05 interruption/contention and H33 replay/idempotency. It requires all 180 incomplete diagnostics and keeps the valid bow visible. It never changes original donor files.

`source.publication` uses the same writer in owned native Node subprocesses. Four workers pause observably at locked, staged, validated and before-commit boundaries and are terminated with bounded descendant cleanup. A separate competitor fails at the existing lock. Current validated bytes remain unchanged; explicit dead-owner recovery removes only orphaned owned data. Further controls reject live/wrong recovery, regressed/altered output identity, absent media, original-root destinations, path escapes, device paths and real junctions. Three fresh re-publications/imports retain the selected identity and compose two explicitly shared outputs without collapsing their obligations. H05/H33 source outcomes remain distinct from their final native/judgment ownership.

Each invocation owns an ignored `.phase4/runs/<nonce>/` directory containing inputs, exact failures, actual process commands/stdout/stderr, interrupted-run records, diagnostics, publication pointers/generations and final results. Failures remain failures after later restoration. Runtime evidence is never copied over a previous invocation or silently promoted to production acceptance. The plan summary records exact final invocation identities and evidence limits.
